# Правила работы над Voice Assistant Core

Этот файл действует для всего репозитория. Более вложенный `AGENTS.md` может
уточнять правила только для своей директории.

## Основные принципы

- Основная платформа — Windows 10/11, язык ядра — Rust.
- Сохраняйте независимость ядра от GUI и конкретных внешних движков.
- Делайте минимальное изменение, решающее реальную задачу. Не добавляйте
  абстракции, зависимости и конфигурацию «на будущее».
- Сначала ищите существующий тип, helper или принятый паттерн в репозитории.
- Исправляйте корневую причину в общем слое, а не отдельный симптом у вызывающей
  стороны.
- Не смешивайте несвязанные изменения в одном pull request.

## Архитектурные границы

- Направление зависимостей:

  ```text
  GUI / CLI
      → versioned IPC
      → Assistant Runtime
      → Audio / VAD / KWS / STT / Models / Commands
  ```

- GUI взаимодействует с ядром только через версионированный IPC-контракт.
- STT, VAD, wake word и источники моделей должны оставаться заменяемыми
  адаптерами.
- Audio callback не выполняет inference, файловый I/O, тяжёлое логирование,
  пользовательские команды или продолжительные блокировки.
- Все аудиоканалы и очереди должны быть bounded; переполнение должно иметь
  явную политику и метрику.
- Тяжёлый или нативный inference выполняется через отдельный worker либо
  `spawn_blocking`.

## Безопасность и приватность

- Никогда не передавайте распознанный текст напрямую в `cmd.exe`, PowerShell
  или другой shell.
- Выполняйте действия только через зарегистрированные типизированные handlers
  и allowlist параметров.
- Проверяйте входные данные на границах конфигурации, IPC, моделей и команд.
- Команды высокого риска всегда требуют подтверждения.
- Для обработчиков обязательны timeout и ограничение параллелизма.
- Не сохраняйте аудио и полный транскрипт по умолчанию.
- Не коммитьте модели, WAV-файлы, логи, токены, пароли и персональные данные.
- Не выполняйте remote code и скрипты из модельных репозиториев.
- Production-модель должна иметь фиксированный commit SHA, отдельную папку
  ревизии и проверяемый SHA-256 manifest.

## Модели

- Структура хранения:

  ```text
  models/<model-id>/<revision>/
  ```

- Загрузка, верификация и inference являются разными операциями.
- Установка выполняется во временную директорию, затем проверяется и
  активируется атомарным переименованием.
- После установки модель должна работать без сети.
- Добавление обязательного файла модели требует обновления manifest,
  верификации и инструкции установки.

## Код и зависимости

- Соблюдайте MSRV из `rust-toolchain.toml`.
- Предпочитайте стандартную библиотеку и уже подключённые зависимости.
- Новая зависимость требует конкретной необходимости и проверки лицензии.
- Ошибки библиотечных слоёв должны быть типизированы; `anyhow` допустим на
  уровне приложений.
- Публичные IPC-типы должны сериализоваться через Serde.
- Не используйте `unwrap`/`expect` на данных пользователя или внешних
  ресурсах. В тестах они допустимы.
- Не подавляйте предупреждения без объяснимой причины.

## Проверки

После изменений выполните:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
```

При изменении публичного API или документации дополнительно выполните:

```powershell
$env:RUSTDOCFLAGS = "-D warnings"
cargo doc --workspace --all-features --no-deps
```

- Нетривиальная ветка, parser, state transition, policy или обработка аудио
  требует минимального теста, который ломается при регрессии.
- Аппаратно-зависимые изменения должны иметь описанную ручную проверку.
- Изменения STT/KWS проверяйте реальным WAV и фиксируйте ожидаемый результат,
  не добавляя приватные записи в Git.

## Обязательное обновление документации

После любого нового поведения, пользовательской функции или изменения
существующего поведения обязательно:

1. обновите `README.md`, если меняются возможности, требования, команды,
   конфигурация, структура каталогов или быстрый старт;
2. обновите `docs/index.html`, если меняются использование ядра, архитектура,
   API, IPC, безопасность, модели или способы расширения;
3. обновите Rustdoc-комментарии при изменении публичного типа, trait, функции,
   ошибки, состояния или протокола;
4. обновите `config/assistant.example.toml`, если добавлены или изменены
   параметры конфигурации;
5. обновите примеры CLI и проверочные команды, если изменился интерфейс
   приложений;
6. проверьте все ссылки и соберите документацию с `RUSTDOCFLAGS="-D warnings"`.

Изменение функциональности без соответствующего обновления README и
документации считается незавершённым.

## Definition of Done

Изменение готово, когда:

- соблюдены архитектурные и безопасностные границы;
- добавлена минимальная проверка нетривиальной логики;
- форматирование, Clippy и тесты проходят;
- README, HTML-документация, Rustdoc и пример конфигурации синхронизированы с
  фактическим поведением;
- в Git не попали модели, временные файлы, аудио, логи или секреты.
